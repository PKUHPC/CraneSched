## 先建立时间线

先问或记录：

- 受影响用户与作业 ID；没有 ID 时记录完整提交命令。
- 首次出现时间、最近一次出现时间和时区。
- 预期行为、实际行为和完整错误原文。
- 单个作业、单个用户、单个分区/节点，还是多个用户共同受影响。
- 最近成功的同类作业 ID，以及本次脚本、数据规模、资源或软件环境的变化。

不要先问“重启过没有”。先确定问题发生在提交、排队、启动、运行、结束或统计阶段。

## 只读证据包

从 [commands-and-states.md](commands-and-states.md) 选择与阶段匹配的本人作业查询：活动作业查 `cqueue`/`ccontrol show job`，结束后查 `cacct`，仅对有代表性的已完成作业使用 `ceff`。不要机械执行全部命令。

需要集群侧信息时，请管理员核对节点/分区状态与原因、用户账户关联、允许的分区与 QoS、资源限制和服务健康情况。向管理员提供作业 ID、时间窗口、完整错误，以及用户已经持有且站点明确公开的资源概况输出；不要让用户试运行集群范围查询来探测权限，也不要提供管理员命令或要求其读取系统配置、服务日志、数据库或其他受限文件。

对机器可读结果可在当前版本支持时使用 `--json`，但用户求助时同时保留人类可读的原始报错。

## 按阶段定位

| 阶段 | 首要证据 | 优先问题 |
|---|---|---|
| 命令执行前/提交被拒 | 完整命令与报错、`--help` | 语法、身份、账户、QoS、分区和资源上限 |
| Pending | `cqueue -j <job_id> -F`、`ccontrol show job <job_id>` | Reason、请求资源、依赖、hold、策略限制 |
| Configuring/Starting | 作业详情、节点状态、持续时间 | 是否短暂过渡，是否集中在节点或分区 |
| Running | 应用日志、节点、可见资源、作业步 | 应用、环境、输入、I/O、并行启动 |
| Completing | 作业详情、持续时间、影响范围 | 是否退出处理延迟，是否节点集中 |
| 已结束失败 | `cacct -j <job_id> -F`、ExitCode、stdout/stderr | 应用返回码、信号、超时、OOM、节点异常 |
| 性能不佳 | 已完成作业 `ceff`、应用时间线 | CPU、内存、I/O、通信和负载规模 |

用 `cqueue -j <job_id>` 查不到作业时转到 `cacct -j <job_id>`。两边都查不到时，先核对作业 ID、数组/步骤 ID 格式、用户权限和时间范围，不要直接判断为数据库丢失。

## 提交被拒绝

按以下顺序排除：

1. 用相应 `<command> --help` 核对当前版本支持的选项和拼写。
2. 核对时间和内存单位、节点数、CPU 数、GRES 格式、依赖 ID 与延迟格式。
3. 若报错涉及身份、账户、QoS 或分区权限，请用户携带原始报错咨询管理员核对关联与限制。
4. 若报错涉及提交数或资源上限，先减少明显过大的请求；仍不明确时咨询管理员。
5. 只有连接超时、RPC 失败或多用户同时失败时，升级为集群服务可用性检查。

用户可自行修正的常见类别：

- 无效时间或内存格式：改为 `00:30:00`、`1G` 等明确格式。
- 节点数大于分区容量：减小请求或改用有权限的合适分区。
- 单作业 CPU、内存、GRES 或时限超限：减小请求，或带业务理由申请管理员调整。
- 依赖作业不存在/已结束：核对 ID 与依赖创建时机，重新提交正确流水线。

管理员侧类别：

- 用户、账户或 QoS 不存在，用户被阻止，身份不匹配。
- 账户不在分区允许列表或位于拒绝列表。
- 内部元数据、数据库写入、服务连接、证书签发或 PMIx/容器运行时错误。

不要通过随意放宽 QoS、分区访问或 `--force` 来“验证”提交问题。

## 作业长期 Pending

先取得当前 Reason：

```bash
cqueue -j <job_id> -F
ccontrol show job <job_id>
```

按原因处理：

- `Held`：确认是否由用户主动 hold。来源不明确时咨询管理员；只有作业所有者明确要求时才建议释放自己的作业。
- `BeginTime`：核对开始时间与时区，等待到设定时间或取消后按正确时间重新提交。
- `Dependency`：检查上游作业状态和依赖类型。
- `DependencyNeverSatisfied`：依赖条件已不可能满足，通常需要取消并以正确依赖重新提交。
- `Priority`：说明作业正在合法排队；核对并发限制与队列政策，不承诺具体启动时间。
- `Resource`：若站点已明确公开资源概况，可用用户已有输出比较请求与当前资源；否则咨询管理员核对节点、GRES 和分区容量。
- `License`：核对自己提交的许可证名称和数量；当前占用情况请管理员确认。
- QoS/Partition 资源限制原因：建议用户等待、减少请求或携带作业 ID 咨询管理员核对限制；不要引导其查询或修改策略。
- `*MetaNotFound`、`*EntryNotFound`：作为集群侧状态异常升级，不让普通用户反复重投。

一个 Reason 可能在前一阻塞解除后变化。每次干预后重新查询，不要假定所有阻塞已解决。

## 作业卡在过渡状态

`Configuring`、`Starting` 和 `Completing` 是合法状态。排障依据是持续时间、重复性和影响范围：

1. 记录状态首次出现与当前时间。
2. 记录本人作业详情中的分区和已分配节点；已有且站点明确公开的资源概况可以附上，节点详情与故障原因请管理员核对。
3. 比较自己在同分区的相似作业是否正常过渡；不要查看其他用户作业。
4. 若集中于单节点，标记节点相关；若跨节点/用户普遍出现，升级为集群侧。

不要仅因看到一次过渡状态就取消作业或排空节点。

## 登录节点能运行但批作业失败

先比较用户可控制的差异：

1. 在作业输出中记录 `pwd`、`command -v <program>` 和必要输入路径的 `ls -ld` 结果。
2. 使用 `#CBATCH --chdir=<shared_workdir>` 固定到计算节点可见的共享目录。
3. 优先在脚本中显式加载模块和激活虚拟环境。
4. 仅按站点指导选择 `--get-user-env` 或 `--export=ALL`，不要盲目同时使用。
5. 不要提交完整环境变量；只保留与程序定位相关且不含敏感值的条目。

若登录节点路径、软件或模块在计算节点不可见，请用户携带作业 ID、工作目录与首次错误咨询管理员，不要读取系统配置或服务日志。

## Running 但应用异常

调度器显示 Running 只证明资源已分配，不证明应用正确工作。检查：

- stdout/stderr 的第一处错误，而不是只看最后一行。
- `ccontrol show job` 中工作目录、命令行、节点、请求与分配资源。
- 应用进程是否在等待输入、数据、网络、许可证或其他 rank。
- 模块/虚拟环境和输入路径是否在计算节点可见。
- GPU/加速器可见性变量是否由调度器设置且未被用户覆盖。
- 多节点任务数、线程数和启动器是否一致。

需要观察作业步时：

```bash
cqueue --step -j <job_id>
ccontrol show step <job_id>.<step_id>
```

只在用户明确希望交互、确认目标是自己的步骤且站点支持时建议 `cattach`。说明它会转发终端输入；附加不是通用性能监控手段。

## 作业结束失败

先查：

```bash
cacct -j <job_id> -F
```

解释时同时使用 `State`、`ExitCode` 和应用日志：

- `Failed` + 非零主代码：通常是应用主动返回失败，先查应用错误。
- 非零次代码：进程收到信号或被调度系统终止，结合次代码含义判断。
- `ExceedTimeLimit`：实际运行超过请求时限；确认是否接近上限、是否需要 checkpoint 或合理增加时限。
- `OutOfMemory`：作业超过分配内存；结合 `ceff`、输入规模和应用日志判断合理内存，而不是无限增加。
- `Cancelled`：确认是否由用户主动取消、上游流程决定或 QoS 抢占。当前文档化的抢占模式会直接取消低优先级作业；是否发生抢占及对应 QoS 策略请管理员核对。

CraneSched 退出码格式为 `主代码:次代码`。主代码是程序返回值；次代码 1-63 通常为信号，64 以上可能是 CraneSched 定义原因。不要只把任何非零次代码解释为应用 bug。

## 性能或资源利用异常

使用已完成且具有代表性的作业：

```bash
ceff <job_id>
```

判断边界：

- CPU 效率低：可能是 I/O、通信、锁、串行阶段或线程未绑定；需结合应用指标。
- 内存效率低：多次同规模作业均低时才逐步降低申请，并留峰值余量。
- 运行变慢：比较输入规模、节点、软件环境、资源争用与历史基线，不把单次波动当回归。
- 多节点扩展差：比较单节点基线、通信占比和每 rank 工作量；更多节点不保证更快。

不要把文档中的固定效率阈值当成服务等级目标。回答应给出下一次可验证的单变量调整。

## 节点或分区异常

用户先保存本人作业信息：

```bash
cqueue --self -F
```

区分：

- `idle/mix/alloc` 是资源使用状态。
- `down`、无响应、`drain` 或附带 Reason 指向节点可用性或管理状态。
- 分区 `down` 与节点资源暂时满载不是同一问题。
- 电源过渡状态可能短暂不可用，应结合持续时间和站点电源策略。

通用 `cinfo` 文档会展示集群范围信息。只有站点用户文档或管理员明确确认这些查询对普通用户公开时，才解释或使用用户已有的最小范围输出；不能通过试运行或等待权限错误来确认授权。若公开信息显示节点/分区不可用，或多个用户同时受影响，请用户提交时间窗口、代表作业 ID 和本人作业输出并联系管理员。不要提供节点管理、分区修改、服务重启命令或受限文件路径。

## 账户权限与 QoS

用户先核对自己作业中可见的 Account、QoS、Partition 和 Reason。若站点允许普通用户查询本人账户记录，再运行：

```bash
cqueue -j <job_id> -F
ccontrol show job <job_id>
current_user=$(id -un) || exit 1
printf 'current_user=%s\n' "$current_user"
cacctmgr show user "$current_user" -P
```

检查关系：

- 用户是否属于提交使用的账户。
- 用户或账户是否被阻止。
- 允许分区和默认/允许 QoS 是否通过账户继承或被用户覆盖。
- 分区允许/拒绝账户列表是否匹配。
- 用户、账户、QoS 和 Partition 的作业数、TRES、时限限制是否与错误一致。

先确认打印出的有效身份就是本人。`cacctmgr` 查询必须显式限定为这个用户；不要使用可能被覆盖的 `$USER`，也不要查询其他用户、账户或全局 QoS。用户仍无法确认允许/拒绝列表、继承或资源限制时，请其携带作业 ID 和原始错误咨询管理员。不要提供任何 `cacctmgr` 写操作、分区详情查询或策略修改命令。

## 容器和作业步

容器排查先查父作业，再查容器步骤：

```bash
cqueue -j <job_id> -F
ccon inspectp <job_id>
ccon inspect <job_id>.<step_id>
ccon logs --tail 100 <job_id>.<step_id>
```

若父作业包含多个节点，查看某一节点上的容器日志时指定该作业分配中的目标节点：

```bash
ccon logs -n <node> --tail 100 <job_id>.<step_id>
```

常见分支：

- 容器功能禁用：管理员侧启用问题，普通用户不能修复。
- 作业 Pending/容器未就绪：先解决父作业调度问题。
- 镜像拉取或启动失败：记录镜像完整引用、节点、首次错误；不要收集仓库密码。
- 多节点日志或交互：先从本人作业详情确认目标节点，再为 `logs`、`attach` 或 `exec` 添加 `-n <node>`；其他确实不支持的操作再缩小为单节点或采用站点支持的编排方式。

只检查已确认属于用户自己的 Pod 和容器 ID。通用文档未说明无过滤的 `ccon pods`/`ccon ps` 只显示本人对象，因此仅在现场帮助或站点文档明确保证本人范围时使用。`inspect`/`inspectp` 用于补充升级证据；不要建议 `--debug-level trace`，因为它可能输出过多环境或实现细节。

作业步资源超过父作业分配时，减少 step 请求或重新申请更大的父作业。取消 `job.step` 只影响该步骤；取消父作业影响所有步骤。

## 变更与恢复边界

用户自身作业的修复建议写清：

1. 目标对象和当前状态。
2. 变更原因与预期影响。
3. 对正在运行和排队作业的影响。
4. 验证命令。
5. 可执行的回退方式。

涉及节点、分区、账户、QoS、预留、许可证、服务或系统文件时停止给出操作步骤，请用户按站点流程联系管理员。只描述现象、影响范围和希望管理员核对的对象。

## 升级材料

无法在用户侧解决时，生成以下最小材料：

```text
影响范围：<用户/分区/节点/作业数量>
时间窗口：<开始时间 - 结束时间，时区>
代表作业：<job_id 或 job_id.step_id>
当前状态：<State + Reason + ExitCode>
已确认：<直接由输出证明的事实>
已排除：<做过的只读检查及结果>
疑似层级：<应用/资源请求/账户策略/节点/分区/集群服务>
最近变更：<已知变更；未知则写未知>
原始证据：<相关命令及脱敏输出>
建议下一步：<一个最小、可验证的检查或已批准变更>
```

不要提交密码、令牌、私钥、完整环境、无关数据内容或整份系统日志。保留时间、作业 ID、状态、Reason、ExitCode 和错误原文。
